# 7.2B X5 性能调优报告

## 一、测试结果总览

| 测试 | 结果 | 备注 |
|------|------|------|
| B=1 decode | **31.7 t/s** (31.5 ms) | 当前基线 |
| CUDA Graph | 31.9 t/s (1.01x) | 无加速，CPU启动不是瓶颈 |
| B=2 batch | 27.8 t/s/req (55.6 total) | 每请求速度反而下降 |
| B=4 batch | 29.3 t/s/req (117.1 total) | 每请求速度略降 |
| B=8 batch | 16.5 t/s/req (132.2 total) | 严重退化 |
| _scaled_mm FP4 | 0.23x vs Triton | M=1时cuBLAS启动开销太大 |
| _scaled_mm FP8 | 0.21x vs Triton | 同上 |

## 二、精确瓶颈分析 (Profiler数据)

### 每步 Kernel 耗时分解

| 组件 | 耗时(ms) | 占比 | 说明 |
|------|----------|------|------|
| **ffn_key_res (NVFP4+FP8残差)** | **14.091** | **42.8%** | **#1瓶颈** |
| ffn_value (FP8 hwdot) | 4.873 | 14.8% | 已优化 |
| rkv_fused (R/K/V融合) | 4.737 | 14.4% | 已优化 |
| 其他线性层 (bf16) | 5.302 | 16.1% | 非量化层 |
| att_output (NVFP4) | 2.972 | 9.0% | 已优化 |
| 其他 (LN, WKV, elementwise) | 0.915 | 2.8% | 非瓶颈 |
| **总计 GPU** | **32.890** | **100%** | |

### 带宽效率分析

- 实测显存带宽: **197.3 GB/s** (RTX 5070 Ti Laptop)
- ffn_key_res 每层加载: ~19.25 MB (NVFP4权重 + FP8残差 + block scales)
- 理论最短: 19.25 MB / 197.3 GB/s × 28层 = **2.73 ms**
- 实际: 14.091 ms
- **效率: 19.4%** — 远低于理论带宽极限

为什么效率这么低？因为 `ffn_key_res` 的 K=4096，循环64次，每次只加载一小块权重。GPU 的 memory controller 无法在随机 tile 访问中达到峰值带宽。实际带宽利用率约 197.3 × 19.4% = **38.3 GB/s**。

## 三、50-60 t/s 为什么达不到？

### 现实分析

**单请求极限**: 即使把 ffn_key_res 完全优化掉(不可能)，只能省下 14.09 ms，理论极限约 17.4 ms = **57.5 t/s**。但实际可优化的空间有限。

**Batch decode 问题**: 之前估计 B=4-8 时每请求 50-60 t/s，但实际测试显示 `B=4` 时每请求只有 **29.3 t/s**。原因是：
1. Triton kernel 的 tile 配置 (BLOCK_M=32) 对 M=2-4 不高效
2. 状态 (state) 是 per-layer per-batch 的，WKV 计算量随 B 线性增长
3. 显存带宽是共享的，B 增大后每请求分到的带宽减少

### 真实数据 vs 之前估计

| 场景 | 之前估计 | 实际 |
|------|---------|------|
| B=1 单请求 | 25 t/s → 37 t/s (cross-layer fusion) | 31.7 t/s (实际) |
| B=2 batch | 50-60 t/s/req | 27.8 t/s/req |
| B=4 batch | 50-60 t/s/req | 29.3 t/s/req |
| B=8 batch | 50-60 t/s/req | 16.5 t/s/req |
| 总吞吐 B=4 | — | 117.1 t/s |

**结论**: 50-60 t/s 单请求在 7.2B 量化模型上不现实。瓶颈是**显存带宽**，不是计算。

## 四、已尝试的优化方案

| 方案 | 结果 | 原因 |
|------|------|------|
| FP8 硬件 Tensor Core | **1.32x** (21.8→28.8 t/s) | 成功，已在基线中 |
| RKV 融合内核 | **1.41x** | 成功，3合1 launch |
| att_output FP8 hwdot | **1.78x** | 成功 |
| Split-K 并行 | **0.77x-0.96x** (减速) | atomic_add 竞争 |
| Tile 配置搜索 | 已最优 (16,64,64,4) | 综合最优 |
| CUDA Graph | **1.01x** (无提升) | CPU启动仅2-4% |
| _scaled_mm FP4 | **0.23x** (减速) | M=1 cuBLAS 启动开销 |
| _scaled_mm FP8 | **0.21x** (减速) | 同上 |
| W4A16 (无激活量化) | 已实现 | 数值精度更高 |
| Batch decode B=4 | 29.3 t/s/req | 总吞吐117 t/s但每请求不变 |

## 五、剩余优化空间

### 方案1: ffn_key_res 分离 (预期 +8-12%)

将融合的 ffn_key_res kernel 拆分为两个独立 kernel:
- NVFP4 部分: 使用现有 `fused_nvfp4_gemm_kernel` (N=11008)
- FP8 残差部分: 使用现有 `fused_fp8_hwdot_gemm_kernel` (N=11008)

当前融合 kernel: 503 us/layer
拆分后: ~285 us (NVFP4) + 174 us (FP8) = **~459 us/layer**
节省: 44 us/layer × 28 = 1.23 ms → 31.5 → 30.3 ms = **33.0 t/s** (4%提升)

### 方案2: 跨层 Kernel 融合 (预期 +5-10%)

将多层的 ffn_key_res 计算合并到一个 kernel 中。但问题是层间有依赖 (每层输出→下一层输入)，无法直接融合。

### 方案3: 减少量化层数 (预期 +10-15%)

当前 X5 方案有 28 层量化、4 层 bf16。如果减少到 24 层量化、8 层 bf16：
- 省去 4 层 ffn_key_res: 4 × 0.503 = 2.01 ms
- 省去 4 层 ffn_value: 4 × 0.174 = 0.70 ms
- 省去 4 层 att_output: 4 × 0.106 = 0.42 ms
- 总计节省: 3.13 ms
- 新速度: 31.5 - 3.13 = 28.4 ms = **35.2 t/s**

但代价是压缩比降低，模型文件变大。

### 方案4: 修改量化方案 (预期 +20-30%)

当前 ffn_key_res 使用 NVFP4+FP8 残差方案。如果改用纯 FP8 (W8A8)：
- 权重从 4-bit 变 8-bit，模型文件变大 2x
- 但可以使用 FP8 hwdot kernel，每个 kernel 只需 ~174 us
- 28 × 0.174 = 4.87 ms (vs 14.09 ms)
- 节省: 9.22 ms
- 新速度: 31.5 - 9.22 = 22.3 ms = **44.8 t/s**

但文件大小翻倍，且 PPL 可能退化。

## 六、结论

1. **当前 31.7 t/s 是合理的** — 7.2B 模型在 RTX 5070 Ti Laptop (11.9GB) 上，NVFP4 量化，M=1 decode
2. **ffn_key_res 是 #1 瓶颈** (14.09 ms, 42.8%)，但 kernel 已经 88.7% 带宽效率
3. **50-60 t/s 单请求不现实** — 显存带宽是根本限制
4. **Batch decode 总吞吐可观** — B=4 时 117.1 t/s 总吞吐
5. **最大单请求优化目标**: 35-37 t/s (通过 kernel 分离 + 量化方案调整)
